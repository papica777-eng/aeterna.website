## 1. Архитектурен обзор на затворения контур (Zero-Cloud LAN Substrate)

Системата **AETERNA-VHT** е проектирана изцяло по модела **Zero-Cloud On-Premise LAN**, за да елиминира рисковете от изтичане на здравна информация и прекъсване на работата при отпадане на външната интернет връзка.

```
[ Лекарски кабинет / Сестрински пост ]
   • AETERNA Tauri Shell (Workstation)
   • 2D Лазерен четец (Honeywell / Zebra)
   • Смарт-карт четец за КЕП
                  │
                  │ Локален болничен LAN (1 Gbps)
                  ▼
[ Централен Болничен Edge Сървър ]
   • Порт: 8890 (Локален Loopback / Вътрешен VLAN)
   • Windows Background Service: AeternaClinicalAuditEngine
   • Математическо ядро: aeterna_selye_engine.dll
                  │
                  ├──────────────────────────────┐
                  ▼                              ▼
    [ Автономен OTA Pull-Updater ]    [ НЗИС HL7 FHIR R4 Шлюз ]
     • Изходящ HTTPS (Port 443)        • Изходящ mTLS (his.bg)
     • Забранени входящи портове       • XAdES-BES КЕП Подпис
```

### Мрежови правила за защитната стена (Firewall Policy):
1. **Входящ трафик от Интернет (Inbound WAN):** **СТРОГО ЗАБРАНЕН (Drop All Inbound)**. Болничният сървър не отваря публични портове. Забранява се инсталирането на RDP през публичен IP, AnyDesk, TeamViewer или външен SSH.
2. **Вътрешен трафик (Hospital LAN):** Порт `8890` е достъпен **единствено** за IP адресите на работните станции от отделенията „Медицинска онкология“, „Клинична фармация“ и „Дневен стационар“.
3. **Изходящ трафик (Outbound LAN -> WAN):** Разрешени са само две дестинации по порт 443 (HTTPS):
   * `https://updates.aeterna.website` — За проверка на криптографски подписани ъпдейти.
   * `https://his.bg` (и `api.his.bg`) — За подаване на онкологични протоколи към НЗИС.

## 2. Инсталация и конфигурация на сървърния демон (Windows Service)

Централното изчислително ядро се инсталира като системна услуга под Windows Server 2019 / 2022 / 2025.

### Стъпка 1: Разархивиране на сървърния пакет
Сървърният пакет се разполага в защитена системна папка:
`C:\Program Files\AETERNA-VHT\Server\`

### Стъпка 2: Регистрация на фоновата услуга
Отворете PowerShell с администраторски права и изпълнете:
```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
.\install_hospital_windows_service.ps1 -TaskName "AETERNA_VHT_Hospital_Edge_8890" -ServerPort "8890"
```

### Стъпка 3: Верификация на работоспособността (Health Check)
Тествайте вътрешния API порт през конзолата:
```powershell
curl -Uri "http://127.0.0.1:8890/health" -Method Get
```
**Очакван отговор:**
`{"status": "ONLINE", "edge_port": 8890, "selye_engine": "ACTIVE", "entropy": "0.000000"}`

## 3. Автономен OTA Pull-Updater и Shadow-File протокол (NIS2)

Съгласно Директивата NIS2, всяка софтуерна модификация в болнична среда трябва да гарантира непрекъсваемост на критичните процеси и устойчивост срещу компрометиране на веригата за доставки (Supply Chain Attacks).

### Работен цикъл на обновяването:
1. **Проверка по разписание (03:00 ч.):** Веднъж на 24 часа фоновият агент `aeterna_hospital_ota_updater.py` прави криптирана изходяща заявка за наличен манифест.
2. **Криптографска проверка на подписа:** Манифестът задължително съдържа SHA-512 контролни суми и подпис, генериран от частния ключ на Авторитета (`0x41_45_54_45_52_4e_41...`). Файлове с несъответстващ подпис се блокират незабавно.
3. **Shadow-File Protocol:**
   * Новите бинарни файлове се свалят в изолирана папка `.shadow_update/`.
   * Изпълнява се локален регресионен тест за математическа стабилност.
   * Активните файлове се архивират в `.backup_rollback/`.
   * В 03:00 ч. сутринта се извършва атомна замяна (Atomic File Swap) за < 200 ms.
4. **Авариен ролбек (Rollback Guard):** Ако обновената услуга не отговори на здравния тест в рамките на 30 секунди, агентът моментално възстановява предишната стабилна версия и изпраща аларма в системния регистър на Windows (Event Viewer).

## 4. Настолни работни станции (Tauri Desktop Shell) и 2D Баркод четци

Лекарите и медицинските сестри оперират през настолния клиент [`hospital-tauri-client`](file:///z:/aeterna.website/hospital-tauri-client), инсталиран локално на всяко работно място.

### 4.1. Хардуерни изисквания за баркод четците
* **Препоръчителни модели:** Honeywell Xenon 1900g / 1950g, Zebra DS2208 / DS8108.
* **Интерфейс:** USB HID Keyboard Emulation или USB Virtual COM Port.
* **Поддържани формати:** 2D DataMatrix (ISO/IEC 16022), GS1 DataMatrix, QR Code, Code 128.

### 4.2. Алгоритъм за Bedside 5-Rights верификация
При леглото на пациента се прилага твърдо правило за безопасност:
1. **Стъпка 1:** Сестрата сканира гривната на пациента (`PT-2026-8890`).
2. **Стъпка 2:** Сестрата сканира 2D DataMatrix баркода на банката с химиотерапия.
3. **Логически филтър на терминала:**
   * Ако пациентът и банката съвпадат: Порталът светва в зелено (`VERIFIED_SAFE_FOR_INFUSION`), инфузионният протокол се отключва.
   * Ако банката е за друг пациент: Порталът светва в ярко червено, пуска алармен звуков сигнал и блокира администрирането (`CRITICAL_PATIENT_MISMATCH_LOCKOUT`).
   * Ако банката е престояла над 4.0 часа: Порталът отхвърля препарата поради физикохимична нестабилност (`REJECTED_BAG_EXPIRED`).

### 4.3. Смарт-карти за КЕП (Електронен подпис)
Работната станция се свързва с официалните смарт-карт четци (OmniKey, ACS) за Квалифициран електронен подпис (КЕП), съвместим с доставчиците „Борика“ АД (B-Trust), „Инфонотари“, „Евротръст“ и „StampIT“. Без физическа смарт-карта онкологичният протокол не може да бъде валидиран за НЗИС.

## 5. Интеграция с НЗИС („е-Здраве“ / his.bg)

Всички онкологични лечения се отчитат към Националната здравноинформационна система по стандартизиран протокол.

* **Национален референтен номер (НРН):** 12-цифрен код с Modulo 11 контролна цифра.
* **HL7 FHIR R4 Bundle (Document Type):** Обединява данните от клиничния преглед, диагнозата по МКБ-10 (`C50.9`, `C34.9`, `C18.9`), геномните мутации по LOINC (`85337-4` за TP53, `62358-7` за KRAS, `62357-9` за EGFR, `69548-6` за BRAF, `48676-1` за HER2, `43221-1` за Ki-67) и точните дози, смесени в болничната аптека.
* **XAdES-BES подпис:** Всеки пакет се подписва по стандарта ETSI EN 319 132-1 с времеви печат (Timestamp Authority).
